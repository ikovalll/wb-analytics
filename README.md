# Отзывы и воронка продаж Wildberries

Сбор данных по товарам магазина через Seller API и подготовка их к
анализу.

## Установка

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

## Настройка

Всё, что может меняться между запусками, задаётся в файле `.env` в корне
проекта (в репозиторий он не попадает):

| Переменная | Обязательна | По умолчанию | Назначение |
|---|---|---|---|
| `WB_TOKEN` | да | — | токен Seller API |
| `WB_NM_IDS` | да | — | артикулы через запятую или пробел |
| `WB_DATA_DIR` | нет | `data` | куда складывать выгрузки |
| `WB_FEEDBACKS_API` | нет | `https://feedbacks-api.wildberries.ru` | хост отзывов |
| `WB_ANALYTICS_API` | нет | `https://seller-analytics-api.wildberries.ru` | хост аналитики |
| `WB_PAGE_SIZE` | нет | `1000` | размер страницы выдачи, максимум 5000 |
| `WB_REQUEST_INTERVAL` | нет | `0.7` | пауза между запросами, секунды |
| `WB_MAX_RETRIES` | нет | `5` | число попыток при 429 и 5xx |
| `WB_TIMEOUT` | нет | `30` | таймаут запроса, секунды |
| `WB_POSITIVE_SAMPLE` | нет | `300` | сколько положительных отзывов на товар класть в подборку для модели |
| `WB_FUNNEL_DAYS` | нет | `7` | глубина воронки в днях, максимум 7 |
| `WB_SPREADSHEET_ID` | для выгрузки | — | ID Google Таблицы из её адреса |
| `WB_SHEETS_CREDENTIALS` | для выгрузки | `service_account.json` | ключ сервисного аккаунта |
| `WB_SHEET_RAW` | нет | `Сырые данные` | название листа с сырьём |
| `WB_SHEET_REPORT` | нет | `Отчёт` | название листа с показателями |

Значения разбираются и проверяются при старте: неверный тип или выход за
допустимые границы дают понятную ошибку до первого обращения к сети.
Переменные реального окружения имеют приоритет над `.env` — удобно для
разовых прогонов вроде `WB_PAGE_SIZE=100 python collect_feedbacks.py`.

Токен передаётся в заголовке `Authorization` **без префикса `Bearer`** —
это особенность WB, со стандартной схемой приходит 401.

## Запуск

Отзывы:

```bash
.venv/bin/python collect_feedbacks.py            # артикулы из .env
.venv/bin/python collect_feedbacks.py 386248405  # только указанные
.venv/bin/python collect_feedbacks.py --verify   # со сверкой полноты выгрузки
```

Воронка продаж:

```bash
.venv/bin/python export_funnel.py                # собрать и выгрузить в таблицу
.venv/bin/python export_funnel.py --dry-run      # только в файлы, без Google
.venv/bin/python export_funnel.py --days 3       # укоротить период
```

### Доступ к Google Таблице

Ключ сервисного аккаунта создаётся в Google Cloud Console (проект → Google
Sheets API → Service account → Keys → JSON) и кладётся в корень проекта.
Отдельно нужно открыть настройки доступа самой таблицы и дать роль
«Редактор» адресу из поля `client_email` в этом ключе — роли уровня проекта
доступ к таблице не дают, и без шаринга приходит 403 при полностью валидном
ключе.

## Что получается

| Файл | Содержимое |
|---|---|
| `data/feedbacks.json` | все отзывы целиком + статистика по каждому товару |
| `data/feedbacks.csv` | тот же массив плоской таблицей, разделитель `;` |
| `data/feedbacks_digest.md` | подборка отзывов для языковой модели |
| `data/funnel.json` | ответ API воронки как есть |
| `data/funnel.csv` | воронка плоской таблицей, артикул × день |

## Устройство

```
wb/config.py     разбор и валидация окружения, объект Settings
wb/client.py     HTTP-клиент: троттлинг, повторы, распаковка конверта ответа
wb/feedbacks.py  модель отзыва и логика сбора
wb/export.py     выгрузка в JSON, CSV и текстовую подборку
wb/funnel.py     период, показатели дня, запрос воронки
wb/sheets.py     запись в Google Таблицу и формулы
wb/styling.py    внешний вид листов
```

## Устройство таблицы

| Лист | Содержимое |
|---|---|
| **Сырые данные** | артикул × день, только числа из API; колонка CR — формула |
| **Отчёт** | по строке на артикул: `SUMIFS`, `AVERAGEIFS`, `MINIFS`, `MAXIFS`, средний чек; строки отсортированы по сумме выкупов по убыванию |

Скрипт пишет в таблицу только сырые числа, все показатели считаются
формулами: их видно, можно проверить и пересчитать без повторного запуска.

Оформление — ширины колонок, шапка, чередование строк, форматы чисел —
задаётся кодом в `wb/styling.py`. Листы пересоздаются при каждом запуске,
поэтому настроенное руками оформление следующий прогон не пережило бы.

## Тесты

```bash
.venv/bin/python -m pytest
.venv/bin/python -m pytest --cov=wb --cov-report=term-missing   # с покрытием
.venv/bin/ruff check wb *.py tests                              # линтер
.venv/bin/ruff format wb *.py tests                             # форматирование
```

94 теста, покрытие пакета `wb` — 97%. Правила линтера и длина строки (88)
заданы в `ruff.toml`. Сеть не используется: клиент
получает подставную сессию, Google — подставную таблицу. Непокрытыми
остались две функции, которым нужны настоящие учётные данные Google.

Что именно проверяется:

| Файл | О чём |
|---|---|
| `test_config.py` | разбор `.env`, границы значений, понятность ошибок |
| `test_client.py` | конверт ответа, повторы на 429 и 5xx, `Retry-After`, отсутствие повторов на 401/403 |
| `test_feedbacks.py` | два прохода по `isAnswered`, пагинация, дедупликация, статистика |
| `test_funnel.py` | границы периода, смена месяца, один запрос на все артикулы |
| `test_export.py` | форматы выгрузки, состав подборки для модели |
| `test_sheets.py` | формулы и их диапазоны |
| `test_sheets_publish.py` | порядок строк, удаление устаревших листов, идемпотентность |

## Регулярный запуск

Скрипт идемпотентен: он пересоздаёт оба листа целиком, поэтому повторный
запуск просто обновляет данные и его можно ставить в расписание как есть.

Запуск раз в сутки в 06:30 через `cron` (`crontab -e`):

```
30 6 * * * cd /путь/к/проекту && .venv/bin/python export_funnel.py >> data/export.log 2>&1
```

Что важно для расписания:

- **Пути только абсолютные.** У `cron` минимальное окружение и другой
  рабочий каталог, поэтому `cd` в начале строки обязателен.
- **Токен и ключ читаются из файлов проекта**, не из окружения командной
  строки, — отдельно прокидывать переменные в `cron` не нужно.
- **Ошибки уходят в лог.** Скрипт возвращает ненулевой код при неудаче,
  так что сбой видно и в логе, и по коду возврата.
- **Время запуска — утро.** Данные за вчерашний день к этому моменту уже
  закрыты, а лимиты аналитики свободны.

Ограничение, о котором стоит помнить: подневная детализация доступна только
за последние 7 дней, и каждый запуск перезаписывает лист сырых данных.
Если нужна история глубже недели, её надо накапливать — дописывать новые
дни к листу вместо замены.

## Решения, принятые по ходу

**Период воронки — последние 7 дней без сегодняшнего.** Сегодня исключён
сознательно: день не закрыт, цифры неполные и портят сравнение по дням.
Подневная детализация у API доступна только за последние 7 дней, поэтому
`WB_FUNNEL_DAYS` ограничен сверху этим значением.

**Один запрос на все артикулы.** У аналитики лимит запросов заметно жёстче,
чем у отзывов, а эндпоинт принимает список `nmIds` — дробить его по товарам
незачем.

**Локаль таблицы выставляется явно.** От локали зависит разделитель
аргументов в формулах, поэтому скрипт фиксирует `ru_RU`, а не наследует
настройку аккаунта. После записи отчёт читается обратно и выводится в лог:
если формула где-то развалилась, это видно сразу, а не при открытии таблицы.

**Средний чек посчитан двумя способами** — по выкупам (сумма выкупов на
количество выкупов) и по заказам. В ТЗ формулировка допускает оба чтения,
и две колонки надёжнее, чем угаданная одна.

**Выкупы отстают от заказов.** Товар едет к покупателю несколько дней,
поэтому за свежие дни выкупов меньше, чем заказов, а в последний день
периода их может не быть вовсе. Это лаг доставки, а не провал продаж.

**Настройки — данными, а не константами.** Артикулы, хосты, размеры страниц
и параметры повторов вынесены в `.env` и собираются в один объект `Settings`.
Модули получают его аргументами и в окружение сами не заглядывают: настройки
видны в одном месте, а функции остаются пригодными для тестов.

**Два прохода по `isAnswered`.** Параметр обязательный и делит выборку
надвое, значения «оба сразу» у него нет. Один запрос вернул бы половину
отзывов молча, без ошибки, — поэтому проход выполняется дважды, а
результаты объединяются с дедупликацией по `id`.

**Проверка полноты.** Флаг `--verify` сверяет собранное с независимым
счётчиком `/api/v1/feedbacks/count`. На момент выгрузки сошлось по всем
трём артикулам: 7 280, 9 117 и 160 отзывов, итого 16 557.

**Повторы запросов.** Клиент выдерживает паузу между вызовами и повторяет
запрос при 429 и 5xx с экспоненциальной задержкой, учитывая заголовок
`Retry-After`. Отдельно разбираются 401 и 403: это проблемы токена, их
повторами не лечат.

**Ответ приходит в конверте.** Эндпоинт отзывов отвечает объектом
`{data, error, errorText}` и умеет вернуть HTTP 200 с `error: true` внутри,
поэтому проверяется не только статус, но и тело ответа.

**Выборка для языковой модели.** Все 16 557 отзывов в контекст модели не
помещаются (778 КБ текста), а обрезка «первых N» уничтожила бы именно
критику. Поэтому подборка смещена в сторону сигнала: отзывы на 1–3★
берутся полностью, на 4–5★ — свежим срезом в 300 штук на товар. Частотность
при этом считается по полному массиву, а не по подборке; в промпте про
смещение сказано прямо. Отзывы без текста в подборку не попадают —
анализировать в них нечего, их оценки учтены в распределении звёзд.
